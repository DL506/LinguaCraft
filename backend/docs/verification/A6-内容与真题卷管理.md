## 1. 交付内容与关键约定

### 1.1 词书与单词(INC-4)

`/api/admin/vocab` 十接口:

| 接口 | 说明 |
|---|---|
| `GET /books` | 词书列表,每行并列 `declaredTotal`(库里写的声明值)与 `actualWordCount`(真实词数) |
| `POST /books` / `PUT /books/{id}` | 新建/更新;`filterLevel ∈ {high,core,cognitive}`,声明总词数不得为负 |
| `PATCH /books/{id}/sync-total` | 把 `total` 显式对齐成真实词数(**唯一**会改 `total` 的入口) |
| `DELETE /books/{id}` | 有单词引用即拒;`book-syllabus` 无条件拒 |
| `GET /words?bookId&level&keyword&page&size` | 列表带 `learnedUserCount` / `favoriteCount` 两个引用数 |
| `GET /words/{id}` / `POST /words` / `PUT /words/{id}` | 详情与新建/更新 |
| `DELETE /words/{id}` | 引用保护删除 |
| `POST /words/import` | CSV 批量导入,见 1.2 |

四条不那么显然的约定:

- **词书是过滤器,不是归属关系**。`vocab_book.filter_level` 与 `vocab_word.level` 之间**没有中间表**,一个单词同时属于所有 `filter_level` 与它同级的词书。所以"把词加进某本书"这件事在数据模型里不存在 —— 后台改的是单词的 `level`。
- **`total` 不自动派生**。种子里 `book-syllabus.total=3000`、`book-high=800`、`book-core=1200`,库里实际只有 20/8/6 个词。若保存单词时自动重算 `total`,首页与学生端词书页的数字会当场暴跌,那是产品决策不是技术决策;所以只在显式点「对齐词数」时才写(`sync-total` 实测:`book-high 800 → 8`)。
- **引用保护删除的依据是 `word_id` 没有外键**。`user_word_progress` / `user_word_review` / `favorite(ref_id)` 任一命中即拒:「该单词已有 2 人在学、被收藏 1 次,不能删除;如需停止投放请修改等级或释义」。删了会留下孤儿行,而"今日待复习数"不 join 词表,会算出学生永远清不掉的幽灵数字。
- **新单词 ID 是 `w-` + 补零递增**。`scanWordIdState()` 取现有数字后缀最大值与位宽,`nextWordId()` 生成 `max+1` 并按位宽补零。种子 ID 是分段的(`w-001..w-008`、`w-101..w-106`、`w-201..w-206`),所以实测下一个 ID 是 **`w-207`** 而不是 `w-021`。学生端列表排序同步从 `ORDER BY id` 改成 **`ORDER BY LENGTH(id) ASC, id ASC`**(`VocabService`),否则 `w-101` 会排在 `w-008` 前面,新词永远挤在 999 之内。

拼写唯一性:库里**没有** `spelling` 唯一键,所以后台只做事前查重并给出可执行的提示 —— 「拼写已存在:lcverify-tmp(词库没有拼写唯一键,请直接编辑那条单词)」,不替你决定该覆盖还是该报错。

### 1.2 CSV 批量导入(INC-5)

`POST /api/admin/vocab/words/import`,`multipart/form-data`,字段名 `file`(前端用隐藏 `input[type=file]`,请求层新增 `upload()` 且**绝不手设 Content-Type**,否则浏览器带不上 multipart 边界)。

- 解析器是自写的 `CsvWordParser`(**不新增 Maven 依赖**):RFC 4180 双引号状态机,支持引号内逗号、`""` 转义、BOM、CRLF;`meanings` 列内部用 `;` 或 `；` 分多条释义。
- 表头必须含 `spelling,phonetic,part_of_speech,meanings,level`,**顺序任意、大小写不敏感**,可以多列。
- 上限 2000 数据行,超出即截断;错误清单最多回报 50 条(`truncated` 字段说明是否被截断);`application.yml` 加了 `spring.servlet.multipart.max-file-size: 5MB` / `max-request-size: 6MB`。
- **重复一律跳过而非覆盖**(库里已有同拼写,大小写无关;或本文件前面行已出现),以免误改已挂学习记录的词条。
- 失败语义分两层(本轮运行期验证时发现并修掉了假成功):
  - **行级**问题跳过并回报,有效行照常入库 —— 一条坏数据不该回滚前面一千九百条;
  - **整单级**问题(文件为空、表头缺列)直接 `code=400` 拒绝。此前表头缺列会返回 `code=0 total=0 inserted=0 skippedInvalid=1`,前端显示"导入完成:入库 0 条",管理员会以为文件是空的。见 `AdminVocabService.java:314-317`、`CsvWordParser.java:85-90`。
- `skippedInvalid = 服务层判掉的等级非法行 + 解析器丢掉的字段不完整行`(`AdminVocabService.java:362`)。之前只用前者,把字段不完整的行漏成了 0。

实测一份 5 行混合脏数据(1 完整 / 1 等级非法 / 1 文件内重复 / 2 字段不完整):

```json
{"total":5,"inserted":1,"skippedDuplicate":1,"skippedInvalid":3,"truncated":false,
 "errors":[{"line":0,"reason":"第 3 行字段不完整(拼写/音标/词性/释义/等级都不可为空)"},
           {"line":0,"reason":"第 6 行字段不完整(拼写/音标/词性/释义/等级都不可为空)"},
           {"line":4,"spelling":"lcverify-f","reason":"level 仅接受 high/core/cognitive,当前为 senior"},
           {"line":5,"spelling":"lcverify-d","reason":"拼写已存在,跳过(不覆盖已有词条)"}]}
```

导入的行**不带词书列** —— 因为词书按 `level` 过滤,新词入库后自动出现在同 `filter_level` 的词书页里,这是模型决定的,不是漏做。

### 1.3 语法管理(INC-6)

`/api/admin/grammar` 七接口:`GET /nodes`(平铺列表,前端按 `parentId` 构树)、`POST /nodes`、`PUT /nodes/{id}`、`PUT /nodes/reorder?parentId=`、`DELETE /nodes/{id}`、`GET /sections/{nodeId}`、`PUT /sections/{nodeId}`。

> 注意 `PUT /nodes/reorder` 的 `parentId` 是 **query 参数**,请求体是**裸字符串数组**(不是 `{parentId, ids}`)。前端 `reorderAdminGrammarNodes()` 已按这个形状调用。

三条不变式:

1. **目录里不允许"点开 404"的叶子**。新建叶节点时在**同一事务**里补建配对章节,`section.id == node.id`(守住 S05 种子的这个约定),正文是占位符「## 待补充 / 本节内容尚未编写。」。分支节点没有正文,`GET /sections/{分支}` 返回 `code=404 该节点还没有正文,请先在节点上新建章节或直接编辑占位内容`。
2. **不能把节点移动到自己的子孙下**(`isDescendant` 沿父链上溯,防成环)。
3. **删除不级联**:有子节点即拒「该节点下还有 3 个子节点,请先删除子节点」;叶子则同事务删掉配对章节。

`reorder` 把给定层的 `sortOrder` 重编为 10/20/30…,并同步章节的 `sortOrder`;不在该层的 ID 拒(「节点 attributive-basic 不属于父节点 tenses,请先改父节点再重排」),不存在的 ID 报 `code=404 语法节点不存在`,空数组报 `code=400 ids 不能为空`。学生端"上一章/下一章"由树的 DFS 顺序推导(`stores/grammar.ts`),**重排即改变浏览顺序** —— 页面上有这句 tip。

### 1.4 真题卷管理与上下架(INC-7)

`/api/admin/exam-papers` 六接口:list(含下架卷,带 `sectionCount` / `objectiveItemCount` / `submissionCount` / `sectionScoreSum`)、detail(含 `content` 与 `answer_key` 两份 JSON)、POST、PUT、`PATCH /{id}/status?status=`、DELETE。

上下架语义(这次特意划清的两条边界):

- **拦**:`ExamService.list()` 加 `status=1` 过滤;试卷详情、开始/继续作答、进度查询走 `findListedPaper()`,下架卷返回 `code=400 该试卷已下架`。
- **不拦**:`buildReport()` 一律不看状态。已经交过的卷子下架后,**成绩报告照常可读** —— 下架是"停止投放",不是"抹掉历史"。实测下架期间 `GET /api/exam/submission/1/report` 仍 `code=0`。
- **删除有引用即拒**:「该试卷已被 1 次交卷引用,不能删除;如需停止投放请使用下架」。
- `status` 参数在查库**之前**校验(否则给一个不存在的值会先 404,管理员看不到真正的原因):`code=400 status 仅接受 1(上架)或 0(下架)`。

`ExamPaperValidator` 四条硬校验(新建与更新都跑,这是本批最危险的写路径 —— 一旦编号错配,客观题会**静默判错**而不是报错):

| 规则 | 违反时的消息 |
|---|---|
| `content` 与 `answer_key` 同 `part` 的编号集合必须相等 | 第 N 部分的答案编号与题目编号不一致(题目:[…],答案:[…]);客观题按编号配对,不一致会静默判错 |
| 答题卡编号全卷唯一 | 答题卡编号 1 在全卷重复出现,判分会串题 |
| `sum(section.score) == total_score` | 各部分分值之和 15 与卷面总分 99 不一致 |
| 恰好一个写作部分且分值为 15 | 写作部分分值必须为 15(异步批改器按此封顶),当前为 X |

写作分值 15 不是随手写的:`ExamAsyncGrader` 用 15 封顶,人工批改抽屉的满分也是从试卷写作部分的 `score` 取(A4-②)。两处口径必须一致,所以宁可在校验里硬拦。

同批拦下的还有:`content 存在重复的 part:1`、`answer_key 多出第 9 部分,卷面没有它`、`第 N 部分缺少写作题目 prompt`、`第 N 部分缺少评分维度 scoringDimensions`。

## 4. 踩坑记录

- **`PageResult` 的列表字段是 `list` 不是 `items`**(`backend/.../common/PageResult.java:21`,前端 `types/api.d.ts:16` 也是 `list`),写验证脚本时读错会让清理逻辑静默不执行(见第 2 节)。
- **`reorder` 的 `parentId` 是 query 参数**:`PUT /nodes/reorder?parentId=tenses` + 数组体。我一开始发 `{parentId, ids}`,得到的是「请求体格式错误」—— 这类"400 但消息很怪"的响应基本都在说 body 形状不对,而不是业务规则不对。
- **不存在的 ID 在重排里是 404、错层是 400**:`findNode()` 先跑,所以 `ids` 里混了拼错的 ID 会得到「语法节点不存在」而不是"不属于该层"。
- **multipart 上传别在请求层设 `Content-Type: application/json`**:项目的 `upload()` 必须完全不设,让浏览器自己带 boundary(见 `frontend/src/api/request.ts`)。
- **上下架的状态校验要放在查库之前**:否则 `status=2` 打在存在的卷上会先命中"试卷不存在"这类误导性分支(`AdminExamPaperService.java:155` 一带)。
- **`exam_paper.status` 用 `TINYINT(1)` + 默认 1**:默认值必须是"上架",否则 V09 执行完所有存量卷都消失,而 `V09` 是幂等脚本(照 V08 的 `information_schema` + `PREPARE/EXECUTE` 写法),重复执行只会输出"已存在,跳过"。

## 5. 数据库变更与备份还原(V09)

V09 执行两次均成功,第二次输出"status 列已存在,跳过""idx_exam_status 已存在,跳过";列与索引已在第 2 节核验。

**我的失误与后果(必须留痕)**:第一次做还原检验时用了 `mysqldump --databases`,导出文件里带 `USE linguacraft;`,于是"还原到临时库"实际把**几秒钟前的导出内容重新灌回了生产库**。事后核对确认无数据丢失(17 张表;`question` 15、`practice_submission` 4(含 #2 pending)、`exam_submission` 1、`grammar_node` 18 / `grammar_section` 12、`vocab_word` 20,自增值 5/2/5 与预期一致),随后按正确姿势(不带 `--databases`,确认导出文件里 `USE` 行数为 0)重跑了一遍还原检验才执行 DDL。教训:**带 `--databases` 的 dump 不能用于"还原到别的库"的验证**。

## 6. 边界与已知取舍

- 单词 CSV 导入不做"更新已有词条"(重复一律跳过),因为覆盖会连带改掉已挂学习记录的词条;要做词库订正请在列表里逐条编辑。
- 单词没有拼写唯一键,后台只做事前查重,不加唯一索引(改索引属于数据迁移,风险另议)。
- 词书 `total` 与真实词数的偏差**保留**,只提供显式 `sync-total`;自动派生会改动学生可见数字,属产品决策。
- 语法重排的 `sortOrder` 采用 10/20/30 步长,留出插队空间;但种子数据用的是 1/2,重排后同层会出现两种数值并存 —— 只影响绝对值,不影响顺序。
- 语法章节正文没有版本历史/草稿态,保存即生效;没有富文本编辑器,直接写 Markdown 原文。
- 真题卷管理不做:复制整卷、按部分追加题目、AI 出整卷(出题仍是单题粒度,见 A3)。
- `PATCH /api/admin/**` 依赖 A2 时补上的 CORS 与 SecurityConfig **两处** `allowedMethods` 同时含 `PATCH` 才可用(见 A5 文档),这次没有再踩。
- 待你验收后再决定:学生端"待复习数"依赖本次 `VocabService` 的孤儿行过滤修正,如果历史库里已有孤儿 `user_word_review` 行,数字会**变小**并立即生效,这是修复不是回归。
