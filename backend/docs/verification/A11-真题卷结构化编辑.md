# A11 · 真题卷结构化编辑 + 卷内解析生成(闸门编号口径修正 + 偏移量由数据推导)

> 2026-10-13。两件交付物:①两个裸 JSON 文本框换成「分部分 → 每道题一行(卷面与答案同排)」的表单,
> 编号不再由人手写:行的位置就是题序,题序 + 前序部分题量就是答题卡卡号;
> ②`POST /api/admin/exam-papers/ai-explain` 按部分让 AI 补中文解析,只产解析不产答案,逐项采纳(见 §7)。
>
> 但这一项的**主线是修闸门**。`ExamPaperValidator` 的第三条规则从 A6-③ 写下那天起就和种子卷互不相容,
> 后果是「真题卷管理一保存就废」——这张卷改个标题都存不下去。

## 1. 实测:唯一的种子卷从来没通过自己的闸门

不改任何数据地做一次往返:

```
GET  /api/admin/exam-papers/exam-2026   → 把返回的 content / answerKey 原样 PUT 回去
PUT  /api/admin/exam-papers/exam-2026   → code=400
      第 2 部分的答案编号与题目编号不一致(题目:[1, 2, 3, 4, 5],答案:[16, 17, 18, 19, 20]);
      客观题按编号配对,不一致会静默判错
```

数据没动:400 在写库之前抛出,前后 `MD5(content)=046fb4d8…`、`MD5(answer_key)=5ce4cd7e…` 一致。
也就是说 A6-③ 之后这条写路径对**仓库里唯一的真题卷**从未可用过。

## 2. 错的是闸门,不是种子

编号口径在产品文档里从头到尾是一致的:

- 任务书 11.7:**「全局编号 = 之前各 section 的题目总数累加 + 本节内题序」**
- `S03__seed_exam_2026.sql` 文件头:**「answer_key.items[].id 为答题卡全局编号(阅读 1-15 / 五选五 16-20 / 完形 21-35 / 语法 36-45)」**
- `ExamService.gradeObjective` 只按 `answer_key` 的全局编号配对学生作答
- 学生端 `ExamPaper.vue` 用 `objective[15 + blank.id]`、`objective[20 + blank.id]`、`objective[35 + blank.id]` 换算

即:**卷面存局部题序,答案存全局卡号**。旧规则要求两个集合相等,只有「全卷恰好一个客观题部分」时才成立。
而它的测试 fixture 正是只造了 `part1 阅读 + part5 写作` —— offset 恒为 0,错规则一路绿灯。
**库里真实那张卷从来没被喂进过测试**,这是典型的"fixture 自己圆了自己的谎"。

## 3. 新规则(`validateNumbering`)

按 `part` 升序遍历所有非写作部分(数组书写顺序不影响结果):

1. 卷面题号集合必须恰为 `{1..n}`;
2. 答案编号集合必须恰为 `{offset+1 .. offset+n}`;
3. `offset += n`。

原来的「answer_key 多出卷面没有的部分」「重复 part」「分值之和≠总分」「写作恰好一个且 15 分」全部保留。
报错文案带上推导过程(`答案编号必须是答题卡全局编号 16~20(前序共 15 题)`),
管理员一眼能分清是**题量对不上**还是**编号写错**。

## 4. 两条测试把闸门与种子咬死

- `ExamPaperValidatorTest` **10 → 14 例**:新增「种子形状的多部分卷应通过」(就是那份被误拒的卷的阳性对照)、
  sections 数组乱序不影响、跨部分答案块重叠、卷面误用全局编号、题量与答案条数不等。
- 新增 `ExamPaperSeedConsistencyTest` **2 例**:直接从类路径上的 `db/S03__seed_exam_2026.sql` 取出两份 JSON 喂给闸门,
  并断言答案编号区间是 `1-15x15 / 16-20x5 / 21-35x15 / 36-45x10`。
  今后任何一边改编号口径,这条测试立刻红。

  踩到的坑:种子里 JSON 的引号写作 `\\"\`(MySQL 反转义后才是 JSON 的 `\"`),
  按大括号配对直接切会把字符串边界判错;正确做法是**先按 SQL 字面量找闭引号,再做 `\\`→`\` 反转义**,然后交给 Jackson。

## 5. 学生端:偏移量由数据推导

`ExamPaper.vue` 原本把 `15/20/35/45` 写死在模板和 4 个函数里(答题卡格数也写死 45)。
现在统一由 `numberings` 按 `paper.sections` 的 part 升序累加推导:起始偏移、区间、格数、
`answeredInPart`、`usedMatchingKeys`、完形/语法的「卡号→局部」回映、答题卡点击跳转部分都走这同一份推导。

种子卷上逐格行为与改造前一致(见 §7),但从此不再依赖「这张卷恰好是 15/5/15/10」这个假设。

## 6. 编辑器怎么做(`ExamPapers.vue`)

- 每个部分一个 Tab(可增删部分、改题型与本部分分值);部分内**每道题一行,卷面字段与答案字段同排编辑**——
  再不需要在两个文本框之间来回数编号。
- **编号不进表单**:行位置 → 题序 → 卡号,只读展示为「题序 3(卡号 18)」。
  这一条比"把服务端四条规则搬上前端"更根本:错不了的就是没法写错的东西。
- 阅读按「篇」分组(多篇文章,题序跨篇连续);五选五带候选句池;完形/阅读带选项行与正确项下拉;
  语法填空带提示词与「可接受变体」;写作带要点、词数、4 个评分维度与范文。
- 未知字段 passthrough:`mergePreserve(original, built, modeled)`(与 A8 同一思路),
  库里 `source`、文章节点自身的 `id` 等没有表单的键原样带回。
- 保存前红绿灯 = 服务端四条硬规则的客户端镜像,另加三类服务端不查但同样会静默判错的坑:
  正确答案不在选项里、选项文本为空、答案解析缺失(后者只提醒不拦)。
- 「预览将要提交的 JSON」折叠面板显示实际提交体,不再有可编辑的裸 JSON 入口。
- 按计划不做拖拽排序。

## 7. 卷内解析生成(`POST /api/admin/exam-papers/ai-explain`)

第二件交付物。为什么不能复用 A10 的 `ai-review`:整卷题目不在 `question` 表里(它们在 `exam_paper` 的两份 JSON 里),
A10 那个接口按题目 id/单题形状走,够不到这里。

**粒度是「一个部分」而不是整卷**。整卷 45 题按 5 题一批要 9 批,同步等一次是三五分钟;
一个部分只有 1~3 批(实测五选五 5 题 **8.4 秒**)。UI 上的按钮就放在每个客观题部分底部。

**只产解析,不产答案建议**。返回结构只有 `{id, explanation}` —— 服务端 DTO 里根本没有 `answer` 字段,
所以"AI 顺手改答案"这条路径在类型上就不存在。A10 里那条「答案可疑不给采纳按钮」的纪律,在这里变成了「压根不接这个字段」。

**送出去的是 `buildPayloads()` 的产物**,也就是点保存时真正提交的那份形状 —— 不会出现"AI 看着表单、存的却是另一份"。

服务端五道清洗(`AiExamExplainService`,10 例测试逐条钉住):

1. **卡号必须属于本批发出去的编号**,否则整条丢弃并计数。真题卷的编号是全卷累加的卡号,
   模型一旦按"局部题序"自己编号,采纳后解析就写到了**别的部分的题**上 —— 比没解析更糟;
2. 解析去空白,空的丢弃(空建议进表单只会把已有解析抹掉);
3. **没有标准答案的项不发往模型**,计入 `skippedNoAnswer`;本部分全是没答案的题直接拒绝,不花额度;
4. 超过 600 字截断(防模型跑飞把上千字塞进 `answer_key`);
5. 跨批同卡号只保留先到的一条。

另外写作部分直接拒(`写作部分没有客观题解析可生成(请改用批改工作台的 AI 评分与范文)`),非法题型 1004 不触模型。

**采纳 UI**:面板按行显示「卡号 / 现有 / 建议」+ 单条「采纳」,
批量按钮是**「只填空白解析」**——已有解析的行必须逐条点,免得把人工写的解析冲掉(实测点了给的是
「没有空白解析的行(已有解析的请逐条采纳)」)。采纳只写进表单,仍需「校验并保存」才落库。

## 9. 有意不做与遗留风险

- **文章里的 `[[n]]` 占位仍显示局部题序**,而答题卡显示卡号(种子卷一直如此,`ExamPaper.vue` 老注释也写了「文章占位保持局部编号展示」)。
  要统一成显示卡号,得连带改写存量 `passage` 文本,收益只是观感一致 —— 没做。
- MSW 离线层(`mocks/handlers/exam.ts`)仍写死 15/20/35 换算,只在 `VITE_USE_MOCK=true` 时生效;
  本仓库联调配置是 `false`,真机路径已按数据推导。
- **改已发布卷的题目数量会让进行中的作答进度错位**:`exam_progress.objective` 的 key 是卡号,
  数量一变后续部分的卡号整体位移。模考期间应先下架该卷。这条没有代码护栏,只在此写明。
- 不做拖拽排序、不做整卷复制、不做 AI 出整卷。
