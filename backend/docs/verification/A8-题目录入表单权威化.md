# A8 · 题目录入表单权威化 + 未知字段 passthrough

> 2026-10-12。改动集中在 `frontend/src/views/admin/QuestionEdit.vue`(553 → 660 行),**零 Java 改动**。
> 目的:让非专业人员只填表单就能录完五种题型,并且"打开老题什么都不改再保存"不再静默改写库里没被表单建模的内容。

## 1. 改动前的事实(接手者需要知道的起点)

- 提交走的是 JSON 面板:`onSave()` 直接 `JSON.parse(contentJson/answerKeyJson)`,**从不调用 `buildPayloads()`**,表单只是面板的上游输入。
- 更糟的是**打开编辑页那一刻面板就被表单洗过一遍**:`loadForEdit()` 先逐字段改 `form`、最后才把库里原始 JSON 写进面板,而 `watch(form, …, {deep:true})` 的 pre-flush 回调在这**之后**又跑了一次 `syncFromForm()`。
  实测(改动前):库里 `cloze-teacher-1` 的 `content` 键集是 `id/type/blanks/source/passage`,而面板第一个键是 `passage`。
- 今天被洗掉的 `id/type/source` 不构成数据损失,因为服务端 create/update 都强制覆写它们(`AdminQuestionService.java:177,219,312,329`);
  真正会出事的是**将来 content 里多一个表单没建模的键** —— A10 的校核标记就是第一个候选。

## 2. 现在的设计

| 机制 | 实现 |
|---|---|
| 反填期间不重生成 | `hydrating` 标志:`loadForEdit()` 全程置 true,面板写入原始 JSON 后 `await nextTick()` 再放开(watcher 排在同一次 flush 队列里,必须等它跑完) |
| 未知字段 passthrough | `buildPayloads()` 改为"**库里原始对象打底 → 表单值覆盖建模键**":顶层用 `mergeTop(original, built, MODELED)`,每条小题/空位用 `mergeItem(row.originalContentItem / originalKeyItem, built, removed)`;`RowModel` 因此新增三个 `original*` 字段 |
| 编号不重排 | `resolveRowIds()`:有原编号的照原样用,只有新增行从当前最大编号往后**续号**(界面每行头部显示「编号 N」而不是数组序号,避免"第 3 行但编号 11"看错) |
| 形状保留 | `acceptAlternatives` 只有在管理员**真的改过这一格**(文本与原始推导文本不同)时才写数组或删键;没动过时 `null` / `[]` / 缺键三种形状逐字保留。`hint` 留空才是真的删键 |
| 权威性反转 | 默认以表单为准;`onSave()` 里 `manualJson` 为 false 时提交合并结果并让面板与之一致(面板即"将要提交什么"的预览)。管理员在面板里动过手才以面板为准,顶部提示语明确说出"以本面板为准" |
| 高级区 | JSON 面板收进 `n-collapse`,默认折叠,标题动态显示当前权威方(`advancedTitle`)。**没有做成 `n-tabs`** —— 表单与 JSON 不是同一面板的两个视图,单标签的 tab 组反而更难懂 |
| 变体入口 | 语法填空的"可接受变体"从第 4 列小格提升为独立虚线区块,带说明(为何要填、只影响这一空、大小写已由答题设置兜住);其他题型显示一行"本题型按精确比对,不支持变体",不给假入口 |
| 错误内联 | `catch` 不再空吞:报错文本钉在页面顶部(`saveError`),并用 `errorRowIndexOf()` 从 `answer_key.blanks[2].answer 不能为空` 解析出**数组下标(0 基)**给对应行加红框 |

## 4. 有意不做的

- 不引前端测试框架(vitest 等)。"未知键被带回"的可自动化契约落在服务端(第 7 项),前端用上面的浏览器往返脚本手验,脚本留在 `backend/target/a8-*.mjs`。
- 不做拖拽排序/行移动:一旦允许移动,`resolveRowIds()` 的"沿用原编号"就会与视觉顺序不一致,需要单独设计(留给你若要给空位重排时)。
- 不动 `QuestionContentValidator` 的任何一条规则,前端 `precheck()` 也只提前报同一类问题,不放宽。
- 不改完形/阅读/五选五的判分:它们仍是精确比对,界面如实说明而不是给一个不生效的变体框。

## 5. 已知边界

- `mergeItem` 依赖"表单行的顺序与库里数组顺序一致"来对齐原始项(按 `id` 匹配,匹配不到则视为新增行续号)。删中间一行会让剩余行编号出现空洞(如 1,2,4),而 `[[n]]` 占位符集合与编号集合必须相等,所以**删空位必须同时改文章正文** —— 这条由服务端第 5 道校验兜住,报错会内联到具体行。
- 高级面板的手工编辑优先级是"整块为准":管理员改过的内容不会再被表单覆盖,这是有意取舍(否则等于否定他们的手上改动),提示语负责说清楚。
