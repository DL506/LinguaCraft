# A10 · AI 校核/补全单题（可接受变体 + 解析校核 + 答案可疑）

> 2026-10-12。一个入口产出三类建议，**逐项人工采纳**，服务端与前端都不写库；点保存才落库。
> 前置：A8 的表单权威性（建议采纳进表单而非 JSON 面板）、A8 前置的 4 维口径、以及本次先补的判分回归测试。

## 1. 为什么先补判分回归测试

A10 是唯一会**批量改写 `answer_key`** 的功能，而判分主链路此前零测试覆盖（交接文档 3.13）。
所以先建 `ObjectiveGradingServiceTest`（11 例）把"什么算答对"钉住：trim、大小写策略、
`acceptAlternatives` 的三种存量形状（数组 / `null` / 缺键）、未作答计为错误但计入总数、
非语法填空走精确 key 比对、单题分缺失按 1 分兜底。判分代码本身没改。

## 2. 接口与产品边界

- `POST /api/admin/questions/ai-review`，请求体是**表单当前的** `{type, content, answerKey}`。
  收整份内容而不是题目 id，所以新建题与 AI 草稿在保存前就能校核，也避免"改了表单却校核库里旧版本"。
  本接口**不读库也不写库**。
- 刻意**不跑五道闸门**：闸门会拒"答案不在候选项内"这类结构缺陷，而那正是希望校核暴露的问题之一。
- 三类建议的处置方式不同，这是有意的：

  | 建议 | 能否一键采纳 | 理由 |
  |---|---|---|
  | `acceptAlternatives`（可接受写法） | 能（并集写入，不覆盖已填的） | 只放宽判分，不动标准答案 |
  | 解析改写 | 能（整条替换该行为准，可再手改） | 解析不下发判分逻辑，只影响学生看到的解释 |
  | 标准答案可疑（`mayBeWrong` / `notUnique`） | **没有采纳按钮** | 答案键影响此后所有学生；AI 只能提醒，改动必须经人 |

- 抽屉底部固定写明"仍需点「保存修改」才对学生生效"，避免把"采纳"误解成"已入库"。
- 只在录入页提供，不影响学生端与判分链路；不注册 MSW handler。

## 3. 服务端不指望提示词兑现（四条清洗，各有测试）

模型返回先过 `AiReviewService` 的清洗，再看提示词写了什么：

1. **编号必须存在于当前 answer_key**，否则整条丢弃并计入 `droppedCount`（界面如实提示"模型另返回了 N 条无法对应的内容"）；
2. **非语法填空一律抹掉 `alternatives`**——判分不读这个键，给采纳按钮就是假承诺（完形/阅读/五选五按 key 精确比对）；
3. **风险值归一到白名单**（`ok` / `mayBeWrong` / `notUnique`，`ok` / `mismatch` / `tooThin`），未知值按 `ok`，前端不会渲染出未定义状态；
4. **变体去空白、去重，并剔除与标准答案同名的项**（否则采纳后变体里混着标准答案自己）。
5. 分批之间**按编号去重**，同一编号只保留先到的一条。

## 4. 一个必须记下的坑：AI 调用有**两层** 60 秒限制

第一次真实校核 10 空的语法填空时，稳定在 60.5 秒失败，报的是
`com.openai.errors.OpenAIInvalidDataException: Error reading response`（响应读到一半被切断），**不是**我们的"AI 服务响应超时"。

排查结论（都实测过，别照抄直觉）：

- 抬 `spring.ai.openai.timeout` 与 `spring.ai.openai.chat.timeout` 到 200s —— **无效**，仍 60.5 秒被切断；
- 真正生效的是 **`spring.ai.openai.chat.options.timeout`**（三个同名属性里唯一"无默认值"的那档），设 180s 后调用能活着回来；
- 但只放宽 HTTP 层还不够：应用层 `AiChatService` 的 `CompletableFuture.get(timeout)` 也是 60 秒，日志会留下 `AI 调用超时(>60 秒)`。
  实测中间那次就是"底层放宽了、我们这层先掐"，85 秒总时长里第二批在 60 秒被我们自己终止。

所以现在是**两层一起放宽、且只放宽校核这一条路径**：

| 配置 | 值 | 作用范围 |
|---|---|---|
| `spring.ai.openai.chat.options.timeout` | 180s | HTTP 客户端（全局） |
| `lc.ai.timeout-seconds` | 60s（不变） | 出题 / 作文判分 / 预评的应用层等待 |
| `lc.ai.review-timeout-seconds` | 180s | 仅单批校核的应用层等待（`AiChatService.chatForJson(prompt, timeoutSeconds)` 重载） |

另外把一次请求**按 5 个编号分批**（`REVIEW_CHUNK_SIZE = 5`）：5 项一批实测 15~40 秒，天然待在限制内；
10 空题两批合计约 54~86 秒。UI 提示语按这个数字写，不是猜的。

## 5. 分批带来的一个假问题（已被真实返回抓到）

分批后每批都发**完整题面** + **半批答案键**，模型于是回报
"答案键仅含 6-10，缺 1-5" —— 这是**假的**，表单里 10 个空都有答案。管理员看了会以为题目坏了。

修法：提示词显式给出"本批只校核这些编号 … 其中不属于上述编号的空位/小题由别的批次负责，本批一律不评、也不要报告答案缺失"。
`AiReviewServiceTest` 里有一条用例专门断言两批各自的编号集合（1-5 / 6-7），防止回归。

## 7. 有意不做

- **不做事后改判**（对已判错的提交让 AI 仲裁翻案）：`recordMistakes` 已写进错题本，改判必须同步撤错题本行，否则"分数改了、错题还在"。
- **不做 `has_answer` 置 0 的副产品**：`has_answer` 是题级不是空级，一个空被判"不唯一"会把整题 10 个空从字符串比对整体切到 AI 判分，界面很难向管理员解释；真要做要单独设计。
- 不做批量校核整库、不做"AI 自动采纳"。
- 不动判分代码：补变体是为了让**现有字符串比对**更准，判分逻辑本身保持零改动。
